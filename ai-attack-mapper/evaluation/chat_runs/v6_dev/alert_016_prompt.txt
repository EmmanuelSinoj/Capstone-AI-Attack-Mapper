## The five-category taxonomy

A -- AI-Assisted Traditional Attacks: AI accelerates a conventional attack technique; AI is
the tool, not the target. Reconnaissance, weaponization, phishing/deepfake delivery, C2,
defense evasion -- including malware or scripts that call an LLM API to generate commands
or code, which is still A (malware calling an API is not an AI agent). Primary framework:
MITRE ATT&CK (near-complete tactic coverage).

B -- Attacks Against AI Systems: the AI/ML model, its training pipeline, or its
distribution infrastructure is the target. Four sub-clusters: prompt injection &
jailbreaking; poisoning & backdoor attacks (training-data/fine-tuning manipulation only --
NOT persistent memory, see D); extraction, inversion & adversarial examples; AI
supply-chain compromise (a poisoned artifact reaching the victim via a registry, package
manager, app store, or repository listing -- the defining feature is the trusted
distribution channel, not just "model tampering"). Primary framework: MITRE ATLAS.

C -- LLM/GenAI Application Attacks: attacks on the application layer around an LLM -- RAG
poisoning and false retrieval entries, RAG privacy/membership-inference/data extraction,
system-prompt and hidden-context leakage, inference-cost attacks, misinformation/ranking
manipulation. Primary frameworks: MITRE ATLAS + OWASP LLM Top 10.

D -- Agentic AI Threats: an AI AGENT -- an LLM-driven system that plans and calls tools on
its own -- is exploited, or is itself the attacker. A model being reachable through an API,
a script that queries an LLM, or exploiting a server that hosts AI is NOT an agent, and is
not D. Tool/API/MCP/SQL/RCE misuse; memory & long-context corruption
(an agent's persistent memory or conversation state is poisoned or manipulated -- this
covers ALL memory/context-poisoning cases, even when the word "poisoning" appears);
multi-agent trust failure and propagation; AI agents autonomously running pentesting or
multi-step attack chains. Requires a joint ATT&CK+ATLAS view. OWASP LLM03 Excessive
Agency applies only when the agent is the victim, not when AI is the attacker's own tool.

E -- Defense & Governance Gaps: not an attack category -- do not assign E to an alert. It
exists only for the literature/control-crosswalk reference; every alert you classify is
an attack and must receive A, B, C, or D.

## How to decide the category (dev-error-informed, v4)

Prompt injection, jailbreaking and "an LLM was involved" are NOT categories by themselves.
They show up in all four categories. Decide by WHO or WHAT is the victim and HOW the harm
happens, using this order -- take the first rule that fits:

1. Supply chain. A poisoned or malicious artifact (model, dataset, package, plugin, agent
   tool, extension) reached victims through a registry, package manager, marketplace, app
   store or repository -> B, "AI supply chain". This holds even if an agent is involved later.
2. AI is only the attacker's instrument. The victim is a person or a conventional system,
   and AI is used to produce the attack: malware written, obfuscated or driven by an LLM
   (including malware that calls an LLM API at run time to get commands), AI-written
   phishing, deepfakes and voice clones for fraud, a public AI service abused as a covert
   command-and-control relay -> A. This stays A even when the attacker had to jailbreak or
   misuse a commercial AI service to get that help.
3. Memory or conversation-state corruption of an AI agent -> D (never B poisoning, which
   is training-data / fine-tuning only).
4. An LLM agent with tools takes the harmful action. Injected or malicious content makes
   an agent run commands, call tools or APIs, read or delete files, or exfiltrate data
   through its tool calls; or AI agents themselves carry out offensive operations
   autonomously -> D ("Agent tool & API misuse" or "Autonomous offensive operations").
5. The victim is an LLM application, its data or its account, with no autonomous agent
   tool action -> C. Includes: RAG poisoning or data pulled out through retrieval; leaking
   chat history, hidden context, system prompts or secrets the assistant can see;
   injected output that the application renders or executes (HTML/JS in replies, plugin
   or code execution -> "Plugin RCE & insecure output handling"); prompt injection aimed
   at LLM-based security tools; stolen API keys or cloud credentials used to consume,
   resell or abuse hosted LLM services, including bypassing a hosted service's guardrails
   at scale ("LLM service abuse & cost").
6. The victim is the model, its training data, or the AI infrastructure itself: training
   or fine-tuning data poisoning and backdoors; model extraction, inversion, membership
   inference; adversarial examples that evade an ML model; exploiting AI infrastructure
   (training clusters, model servers, notebooks) to steal models, data or compute; or a
   direct jailbreak of the model where the jailbreak itself is the whole event -> B.
7. Scope: in_scope is false only if AI plays no real part in the attack. A conventional
   exploit against AI infrastructure is in scope.
8. adversarial is TRUE whenever any attacker, threat actor, criminal group, or red
   team / researchers performing the attack is described -- including attackers who
   abuse an AI service. Set it FALSE only when no one is attacking at all (an
   autonomous system causing harm on its own initiative).

Confidence: 0.9+ only when exactly one rule clearly applies. Use 0.6-0.75 when two rules
were plausible and you chose between them, and below 0.6 when the alert is thin or
ambiguous. Do not default to 0.9.

the ID unusable even when the underlying judgment was right:
